# 仮想カーソル位置 (提案)

**状態: 2026-09-12 実装済み (第一段)。**
Elements 仕様精査 ([ElementsAudit.md](ElementsAudit.md)) §1 / §1-b の作業中に
「実カーソルを直接動かす」構造が生む問題が続けて出たため、構造そのものを
置き換えたもの。下の「実装」節に入った範囲と残りを書いてある。

---

## 1. 何を変えるか

ウィンドウごとに**仮想カーソル位置**を持ち、そこを唯一の真実にする。

| | 現在 | 提案 |
|---|---|---|
| キー / パッドでのフォーカス移動 | `SetCursorPos` で**実 OS カーソルを動かす** | 仮想位置を更新するだけ (実カーソルは触らない) |
| hover 判定 | 実カーソル位置 | 仮想位置 |
| 内部からのカーソル参照 | 実カーソル位置 | 仮想位置 |
| 実マウスの移動 | そのまま反映 | **ウィンドウ内なら**仮想位置を更新。外なら無視 (現状維持) |
| `Agent` のマウス操作 | 実カーソルを動かす | 仮想位置だけ動かす (実カーソルは触らない) |

---

## 2. なぜ (この案が出てきた経緯)

### 2.1 「自分が動かしたカーソルか」の判定が要らなくなる

現在は cursor-warp のたびに **OS を一往復**する:

```
フォーカス移動 → SetCursorPos → OS → mouse move が返ってくる
                                      ↓
                     「これは自分が出した warp の echo か？」を座標で判定
```

この判定が engine (`ElementsDialogManager` の `warp_expect_*`、レイヤ座標) と
elements_modal (`warp_issued` / `warp_target`、view 論理座標) の**両方に独立実装
されていた**。同じ許容幅 ±2px を倍率の違う 2 つの座標系へ当てていたため、
`present_scale != 1` の画面では判定が食い違いうる。2026-09-12 に engine 側 1 か所へ
寄せて `on_mouse_move(..., bool synthetic)` で渡す形にしたが、**これは暫定措置**。

仮想位置なら往復そのものが無いので、`warp_expect_*` も `synthetic` も
**まるごと不要になる**。バグを直すのではなく、発生源が消える。

### 2.2 「直近の操作はキーかマウスか」が推測でなく事実になる

`last_nav_source` (key / mouse) は、実カーソルが唯一の真実であるために
「移動量から推測」している。誤ると、キー操作中なのに hover がフォーカスを
奪って **フォーカスとポインタが 2 項目間で振動し、グリッド状 UI が操作不能**
になる (案件で多発した「連打状態」の正体)。

仮想位置なら**誰が最後に書いたか**が記録として残るので、推測が要らない。
開いた直後の置きっぱなしポインタ対策 (`hover_gate`) も同じ理由で単純化する。

### 2.3 テストが決定論的になる

2026-09-12 の計測で実際に踏んだ:

- cursor-warp の計測が**実マウスの移動で汚染**された
- しかも**オーバーレイが mouse move を消費するのでシーン側では検出できず**
  (`mousemoves` が 0 のまま)、汚染に気付かず **§1-b という誤った不具合を起票**した
  (後に取り下げ)
- 以後の計測は「人がマウスに触らない」という運用制約付きになった

Agent が仮想位置だけを触る形なら、物理マウスが何をしていても再現する。
運用制約が消え、CI 的な自動検証にも載る。

### 2.4 デスクトップを荒らさない

現在はパッド操作のたびに OS のカーソルが実際に飛ぶ。ウィンドウモードでは
ユーザのポインタが勝手に持っていかれる。仮想位置なら自ウィンドウ内の
話に閉じる。

## 2.5 実装 (2026-09-12)

### 入ったもの

- **`common/visual/VirtualCursor.h`** — `tTVPVirtualCursor` (位置 + 有効フラグ)。
  未設定のうちは無効で、読み出し側は実カーソルへフォールバックする
  (起動直後にポインタがどこにあるか分からない状態)。
- **ウィンドウ実装が 1 つずつ持つ** (`win32/environ/WindowFormUnit`、
  `generic/environ/WindowForm` + `sdl3/environ/form`)。書き手と読み手:
  - `OnMouseMove` (実マウス) → 仮想位置を上書き。ここへ来るのはウィンドウ内の
    移動とキャプチャ中のドラッグだけなので、**「ウィンドウ外は無視して現状維持」が
    自動的に成り立つ**
  - `SetCursorPos` (`Layer.setCursorPos` 等) → 実カーソルを動かし、仮想位置も揃える
  - `SetVirtualCursorPos` (新規) → 仮想位置だけ。キー / パッドのナビ用
  - `GetCursorPos` → 仮想が有効ならそれを返す
- **読み出しは 1 か所に集約されていた。** `Layer.cursorX/cursorY` →
  `LayerManager` → `LayerTreeOwner` → `DrawDevice` → `Window->GetCursorPos` と
  一本道なので、ウィンドウ実装を直すだけで全読み手が追従する
  (棚卸しが「一番の手間」と書いたが、実際は層が効いていた)。
- **`tTJSNI_Window::SetVirtualCursorPos`** を追加し、Elements のナビから叩く。
- **Elements の cursor-warp が実カーソルを触らなくなった** —
  `ElementsDialogManager` の warp 要求は `SetVirtualCursorPos` を呼ぶだけ。
- **echo 判定を両側から撤去**: engine の `warp_expect_*` 一式と、
  `overlay_session::on_mouse_move` の `synthetic` 引数。
  `on_mouse_move` へ来る move は**常に実マウス**になった。
- `Agent` のマウス注入は元から `form->OnMouseMove` 経由なので、実 OS カーソルを
  触らず仮想位置だけを更新する形に**自動的になった**。

### 効果 (計測)

`data/elements_audit` シナリオ 1 (矢印キーを 150ms ごとに注入、倍率 1/1 と 1/2):

| | 移行前 | 移行後 |
|---|---|---|
| フォーカス移動回数 (キー 12〜14 回に対して) | 5 / 6 | **13 / 15** |
| 振動 (A→B→A) | 0 | 0 |
| `warp guard` ログ | 出る | **0 件 (機構ごと消滅)** |

**移行前は注入した 13 回のうち 5 回しか実際に動いていなかった** — warp が
生む合成 move が `nav_source` を mouse へ倒し、以後のナビが流れていた。
仮想カーソルにしたことで、注入したぶんがそのまま移動になる。

### 派生: 実マウス入力を捨てる (`-ignoremouse` / `Agent.ignoreRealMouse`)

仮想カーソルにしたことで「入力は全部 Agent が出す」構成が意味を持つように
なったので、**実マウスの入力を捨てるスイッチ**も足した。

- 起動オプション `-ignoremouse=yes`、実行中は `Agent.ignoreRealMouse`
- 実装は `common/visual/VirtualCursor.h` の `TVPIgnoreRealMouse` /
  `tTVPAgentMouseInjectScope`。両ビルドの `TTVPWindowForm::OnMouse*` の入口で
  「無視中 かつ Agent 注入でない」入力を捨てる。Agent の注入関数
  (`TVPAgentInject*`) がスコープガードを立てるので注入だけが通る
- `Agent` が居るビルドでのみ有効にする (Agent の無いビルドで実マウスを捨てると
  操作不能になるため)
- hover 判定もカーソル参照も仮想位置を見ており、その位置は Agent 注入で
  更新されるので、有効にしてもホバー / フォーカスは従来どおり動く

これで「人がマウスに触らないこと」という運用制約が**測定手順から外せる**。
この制約のせいで §1-b の誤った不具合起票が起きたので、その再発防止でもある。

## 2.6 第二段 (2026-09-12)

第一段で残していた 3 点を片付けた。

### クリックは実座標が勝つ

`OnMouseDown` / `OnMouseUp` / `OnMouseClick` が、配送の前に**実座標で仮想位置を
揃える**ようにした (両ビルド)。ユーザは見えているポインタの位置を押しているので、
キー / パッドのナビが仮想位置を別の場所へ置いていても、クリックで揃って
ヒット判定と hover が食い違わない。

### 仮想カーソルを迂回していた読み手を潰した

`::GetCursorPos` (Win32 API 直呼び) を全部洗ったところ、**5 箇所のうち 3 つが
迂回していた**。

| 箇所 | 用途 | 判定 |
|---|---|---|
| `SetMouseCursorState` / `RestoreMouseCursor` | 「隠してから実マウスが動いたか」を見る | **実カーソルで正しい**。そのまま |
| マウスキー機能の位置読み (×2) | Enter / Space / パッド A を «カーソル位置のクリック» に変換 | **仮想へ変更**。実カーソルを読むと、ナビで動かした位置ではなく物理ポインタの場所をクリックしてしまう |
| マウスキー機能の移動 | キーボードでカーソルを動かす | 実カーソルを動かすのが目的なのでそのまま動かし、**仮想位置も揃える**ように変更。揃えないと hover / `Layer.cursorX/Y` が古い位置を指したままになる |

### `mcsTempHidden` まわり

機構自体は従来のまま (warp で隠す / 実マウスの移動で戻す) で正しい。
ただし「cursor-warp が生む合成 move は期待座標一致で再 hide する」という
**前提が消えた**ので、コメントを実態 (ここへ来るのは常に実マウスの移動) へ訂正した。
`ElementsDialogManager` 側の「実カーソルを `SetCursorPos` する」という説明も
「仮想カーソル位置を置く」へ直した。

### 個別検証の結果

- **ヒント (ツールチップ)** — OS のツールチップが実ポインタに追従する形で、
  `GetCursorPos` は経由しない。実ポインタの位置に出るのが自然なのでそのまま。
- **IME** — 変換 / 候補ウィンドウは**キャレット追従**なのでカーソル位置とは無関係。
- **カーソル形状** — マウス移動イベント由来のレイヤヒットテストで決まる。
  パッドナビ中は実カーソルを隠しているので形状は問題にならない。
- `Window.cursorX/cursorY` / `Layer.cursorX/cursorY` は `GetCursorPos` 経由で追従済み。

## 3. 決めておく規則

| 事象 | 規則 |
|---|---|
| 実マウスが動いた (ウィンドウ内) | **仮想位置を即上書き** = 実移動が常に勝つ。hover はフォーカス中の widget から物理ポインタ位置へ移る (現在 `nav_source` が mouse へ倒れたときと同じ挙動なので退行ではない) |
| 実マウスが動いた (ウィンドウ外) | **無視**。仮想位置は維持 |
| クリック | **実座標が勝つ**。ユーザは見えているポインタの位置を押しているので、仮想位置を実座標へ合わせてから配送する |
| ドラッグ | 実押下で始まったドラッグは**実マウス追従**。途中で仮想位置が別を指すと破綻する |
| キー / パッドのフォーカス移動 | 仮想位置をフォーカス先の hot point へ更新。実カーソルは触らない |
| カーソルの表示 | 現在の `mcsTempHidden` の考え方をそのまま使う。**動かさずに隠すだけ**になるので単純化する |
| `Agent` のマウス API | 仮想位置のみ。実カーソルは触らない |

## 4. 作業の内訳

### 4.1 エンジン側

- ウィンドウごとに仮想カーソル位置を持たせる (描画矩形内の座標系。
  現在 `SetCursorPos` / `GetCursorPos` が使っているのと同じ空間)
- 書き手を 3 つに整理: ①ナビ (キー/パッド) ②実マウス (ウィンドウ内のみ)
  ③Agent。「最後に書いたのは誰か」を持てば `nav_source` になる
- **読み出し側の棚卸しが一番の手間**。仮想位置へ向けるものを一覧にする:
  - `Window.cursorX` / `cursorY`
  - `Layer.cursorX` / `cursorY` (`TTVPWindowForm::GetCursorPos` がこの用途と
    コメントされている)
  - ヒント (ツールチップ) の表示位置
  - IME の変換 / 候補ウィンドウ位置 (現在はキャレット追従なので影響は薄いはず)
  - ドラッグ判定 (上表のとおり実追従のまま)
  - カーソル形状の決定 (どのレイヤの上に居るか)

### 4.2 Elements 側

**ほぼ削除になる。**

- `overlay_session` の warp 要求 (`take_key_focus_move`) は「ホストが実カーソルを
  動かす」契約だったが、「ホストが仮想位置を動かす」に読み替えるだけで済む
- `on_mouse_move(..., bool synthetic)` の `synthetic` 引数を廃止
- `warp_target` (診断用に残してある) も廃止
- `last_nav_source` はホストから事実として受け取れるなら、推測ロジックを削除
- `hover_gate` (開いた直後の置きっぱなしポインタ対策) の単純化

## 5. これでは解決しないもの

§5 の「押しっぱなしのボタンが別の画面に効く」はキー状態の話なので、
`armed_vks` / `suspend_pad_nav` / 離しの全インスタンス配送は引き続き必要。
カーソル側の複雑さだけが落ちる。

## 6. 検証

`data/elements_audit` の **シナリオ 1** がそのまま使える。仮想カーソルになれば
「実マウスに触れていると測定にならない」制約が消えるので、判定条件を
「振動 0」だけにできる (現在は `-navlog` の `warp guard: MISMATCH` の有無で
汚染を見る必要がある)。移行前後で同じシナリオを回して比較する。

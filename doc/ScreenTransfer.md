# 画面転送コスト (合成フレーム → GPU テクスチャ)

レイヤ合成が終わった画面バッファを GPU テクスチャへ送る部分の話。
**「fps は出ているのに重い」「実機だけ遅い」の切り分けで最初に見る場所**なので、
経路・計測方法・数値の読み方をここに集約する。

関連: [DrawStats.md](DrawStats.md) (描画スレッドプール利用率) /
[ElementsDialog.md](ElementsDialog.md) (overlay 側の内訳) /
[D3D11Migration.md](D3D11Migration.md) (WINVER の経路と差分更新化の経緯) /
デモ `data/perf_stats` (本ドキュメントの数値を再現できる計測画面)

---

## 1. 経路 (バリアント別)

| バリアント | DrawDevice | 転送 API | 転送単位 |
|---|---|---|---|
| WINVER | `tTVPBasicDrawDevice` (D3D11) | `UpdateSubresource` (+ `D3D11_BOX`) | ダーティ矩形 |
| SDL3 既定 (デスクトップ) | `tTVPOGLDrawDevice` / `SDLOGLDrawDevice` (GLES) | `glTexSubImage2D` (サイズにより PBO) | ダーティ矩形 |
| SDL3 (renderer 経路) | `tTVPSDLDrawDevice` | `SDL_UpdateTexture` | ダーティ矩形 |

共通の考え方は「**CPU 側に合成結果の永続シャドウを持ち、変化した矩形だけ GPU へ送る**」。
GPU テクスチャの内容は保持される前提なので、送らなかった領域は前フレームの内容が残る。

- **WINVER が `DYNAMIC` + `Map(WRITE_DISCARD)` を使わない理由**: WRITE_DISCARD は
  毎回全破棄なので差分更新にならない。`DEFAULT` テクスチャ + `UpdateSubresource` を採る。
- **PBO を使うかの判定 (GL)**: 転送バイト数 256KB 以上で PBO、未満は直接転送が既定。
  小さい矩形を多数更新する画面では PBO の固定コストが不利になるため。
  `System.texUploadUsePBO` (または環境変数 `KRKRZ_GLTEXUP=pbo|direct`) で強制できる。
  **Windows の ANGLE 実装はサイズによらず常に直接転送**なので、この環境では A/B しても差が出ない。

## 2. 計測

いずれもビルドオプション不要で常時計測している (1 フレーム数回のカウンタ加算のみ)。

- `System.renderStats` … 本画面の転送。`texUploadUs` / `texUploads` /
  `texUploadBytes` / `frames`。`System.renderStatsReset()` で 0 クリア。
- `Dialog.renderStats` … Elements overlay 側の内訳 (update / raster / acquire /
  upload / present)。ベンチ画面は `data/elements_bench`。
- **すべて累積値**。2 回読んで差分を取り、経過実時間との比で見る。

カウンタの意味はバリアント間で揃えてある:

- `frames` = **合成フレームを描いた回数** (転送の有無に依らず)
- `texUploads` = **転送 API の呼び出し回数** (= ダーティ矩形の数)

---

## 3. 数値の読み方

### 3.1 転送率が高い = 転送が重い、とは限らない

`転送率 = texUploadUs / 経過実時間`。これが 90% でも **fps が落ちていなければ
転送が足を引っ張っているわけではない**。転送呼び出しの中でドライバが次フレームを
待っている (vsync 待ちを転送が肩代わりしている) ケースが多いため。

判定の目安:

| 転送率 | fps | 解釈 |
|---|---|---|
| 高い | 出ている | 待ちの大半は vsync 同期ぶん。転送は詰まっていない |
| 高い | 落ちている | 本当に転送 (または転送先の GPU 側) が詰まっている |
| 低い | 落ちている | 詰まりは別の場所 (合成・スクリプト・スレッド)。[DrawStats.md](DrawStats.md) へ |

実例: SDL3/ANGLE で 440x502 を毎フレーム全面更新すると
「940KB を 1 回・15.3 ms・転送率 92.8%」になるが fps は 60 のまま。
15.3ms = 1 フレーム時間ちょうどで、これは `glTexSubImage2D` の中で待っている姿。
同じ負荷を WINVER (D3D11) で測ると `UpdateSubresource` が即座に返るので
転送率 1.2% になる。**同じ「重さ」を違う場所で計上しているだけ**で、
バリアント間で転送率をそのまま比べても意味がない。

### 3.2 コストは「面積」ではなく「1 回あたりのバイト数 × 回数」

`data/perf_stats` の実測 (1280x720、毎秒 60 回更新、SDL3/GLES):

| 負荷 | 転送回数 | 転送量 | 転送率 |
|---|---|---|---|
| なし (静止) | 6 回/秒 | 1.8 MB/秒 | 3.0% |
| 18x18 の矩形を 60 個/フレーム | 4192 回/秒 | 6.0 MB/秒 | 3.2% |
| 440x502 を全面塗り | 60 回/秒 | 55.1 MB/秒 | 92.8% |
| 同じ絵で「動いた矩形だけ」更新 | 70 回/秒 | 4.3 MB/秒 | 3.2% |

- **呼び出し回数が 700 倍でも、1 回が小さければ総コストは安い** (2 行目)。
- **全画面を毎フレーム塗り直す作りは、それだけで転送に張り付く** (3 行目)。
- **同じ見た目の変化でも「消す矩形」「描く矩形」だけを `update` すれば 1/13** (4 行目)。

実装上の指針はこれに尽きる: **`Layer.update()` に渡す矩形を必要最小限にする**。
`update()` を引数なしで呼ぶ (= 全面) 癖があると、静止画面でも常時フル転送になる。

### 3.3 静止画面で転送が発生していないか

正しく差分更新できていれば、**画面に変化が無いフレームでは転送 0** になる。
静止しているのに `texUploadBytes` が毎フレーム画面サイズぶん増えていたら、
どこかが全面更新を出している (または DrawDevice が差分に対応していない)。

WINVER は 2026-08-16 まで実際にこの状態だった (毎フレーム 3.5MB 無条件転送)。
差分更新化で静止時 421.9 MB/秒 → 1.8 MB/秒 になった経緯は
[D3D11Migration.md](D3D11Migration.md) の追補節。

## 4. バリアント間で比較するときの注意

同じ負荷を WINVER と SDL3 で測った結果 (1280x720、毎秒 60 回更新)。
1 更新周期あたりのバイト数に正規化してある (fps が違うため):

| 負荷 | SDL3 (GLES) | WINVER (D3D11) |
|---|---|---|
| 18x18 x60 個 | 100 KB/回 (= 18x18x4 × 60、ぴったり) | 738 KB/回 (約 7 倍) |
| 440x502 全面塗り | 918 KB/回 | 763 KB/回 (ほぼ同じ) |
| 中矩形アニメ | 72 KB/回 (= 2 矩形ぶん、ぴったり) | 158 KB/回 (約 2 倍) |

1. **転送率はそのまま比較できない** (3.1 のとおり待ちの計上場所が違う)。
   比べるならバイト数と回数で見る。
2. **DrawDevice へ届くダーティ矩形の粒度がバリアントで異なる**。上の表では
   SDL3 側はスクリプトが指定した矩形がそのまま届いているのに対し、WINVER 側は
   少数の大きめの矩形にまとめられて届く (60 矩形 → 約 10 矩形)。
   畳んでいるのは DrawDevice より手前 (レイヤマネージャの更新領域管理) で、
   **散らばった小矩形が多い画面では WINVER の方が余分に送る**。
   ※ 未調査。粒度を揃えたい場合はレイヤマネージャ側の更新領域合成ルールから。
3. fps 自体が違う (vsync のかかり方・リフレッシュレート) ので、
   「/秒」の数値をそのまま並べない。

## 5. まとめ (チェックリスト)

重い画面に当たったら順に見る:

1. `System.renderStats` の差分を取る (`data/perf_stats` を起動すれば同じ計算をしている)
2. 静止時に転送が 0 になるか → ならなければ全面更新を出している箇所を探す
3. 転送率が高い場合、fps が落ちているか → 落ちていなければ転送は犯人ではない
4. 転送が本当に重いなら、1 回あたりのバイト数を減らす (更新矩形を絞る) 方向で改善する。
   回数を減らす方向 (矩形を union にまとめる) は、面積が増えるので逆効果になりやすい
5. 転送が犯人でなければ [DrawStats.md](DrawStats.md) (スレッド利用率) と
   `Dialog.renderStats` (overlay) を見る
